## Adding a fixture

New fixtures go on the [fixture comparison site](../../README.md#fixture-comparison-site) as well as in this file. Export the page from the device as a PDF and commit it beside the note as `<name>.pdf`: `scripts/build-fixture-site.ts` pairs the two up by name on its own and gives the fixture a page showing the device's vector ink against ours, which is where a rendering change gets judged. An export the device rasterised carries no vector ink and is skipped — unless our own render draws nothing either, in which case the two agreeing the page is blank is worth showing and the fixture appears with its pages marked as having no ink on either side. A `.note` with no export at all still belongs here; it just has nothing to be compared against.

Add the fixture to `FIXTURE_NOTES` in that script at the same time, saying what it isolates and anything surprising about how it renders. A fixture with no entry still appears on the site, but as a bare name with no explanation of why it is worth looking at, and the reasoning below is then the only place it exists.

## Fixtures

'nomad-3.15.27-blank-2p.note' contains two pages of handwritten text, and demos the available writing tools. This was done using the blank background template, and contains a link to the first page on the second page.
'nomad-3.15.27-blank-shapes-and-RTR.note' conains a single page of shapes, patterns, and handwritten text. Headings and keyword highlighting included in file. This file was created using Real Time Recognition (allows export of handwritten notes as text within the nomad), with the blank background template.
'test.note' is the oldest file here — `SN_FILE_VER_20220011`, `APPLY_EQUIPMENT:A5X` — and the only one written with the older pen ids: ink pen `1` (not `16`) and marker `5` (not `11`). Page 1 is two lines of handwriting with a highlighter pass over the first, which is what pins `pen=5` to the marker. It also stores colours as palette *ids* rather than grey levels, and `test.pdf` — the device's own vector export, committed beside it — is what decodes them: `48` is dark grey (157) and `81` light grey (201), each of the export's colour groups covering one of our decoded groups to within a stroke half width. Reading the ids literally used to cost the page 16 of its 58 strokes, dropped by the ink-presence check as invisible. See the `pen` and `color` sections of `plans/vector-format-spec.md`.

'sample.spd' is a synthetic Atelier file (not exported from a real device). Its schema and layout (sparse per-layer tiles, a `surface_9999` "Reference Layer", a `surface_3` layer with no tiles, `surface.width`/`surface.height` config) were cross-checked against a real device-generated `.spd` file to keep it representative.
'real-device.spd' is a real Atelier file exported from a Supernote device: a built-in "Audubon" template background (`surface_9999`) with a couple of handwritten/sketch strokes on `Layer 1`/`Layer 2` (`surface_1`/`surface_2`) and an unused, tile-less `Layer 3` (`surface_3`). Used to confirm the schema, config encoding, and tile-id addressing against real output rather than only a community tool's approximation of the format.

'stroke-isolation.note' isolates one pen-attribute variable at a time, to reverse-engineer how TOTALPATH encodes pen tool, color, and width (issue #56 follow-up: vectorInk currently renders eraser marks as ink and ignores pen type entirely). Pages are 1-indexed below to match how they were authored on-device:
- Page 1: two horizontal strokes; the lower one was fully deleted with the stroke eraser (select-and-delete-whole-stroke, not a pixel-drag erase).
- Page 2: four strokes, one per pen tool, default color, left-to-right/top-to-bottom in this order: needle point pen at width 0.3, ink pen at width 0.5, marker, calligraphy pen at width 0.7.
- Page 3: four needle-point-pen strokes, default width, one per color in this order: black, dark gray, light gray, white.
- Page 4: four needle-point-pen strokes, black, one per width in this order: 1.0, 0.6, 0.3, 0.1.
- Page 5: two marker strokes, default width, in this order: black, then white -- isolates color from a wide (rather than needle-thin) tool, and confirms white ink specifically (RATTA_RLE renders it as opaque `(255,255,255)`, not the transparent-background `alpha=0` a naive "white == blank" check would assume).

'headings-and-marker.note' isolates Supernote's "Heading" feature (circle handwriting, tap the H icon, pick a background -- see https://support.supernote.com/1759244-using-titles-keywords-and-stars) from its marker/highlighter tool, to confirm both decode the same way as stroke-isolation.note's plain ink (issue #56 follow-up). Pages are 1-indexed:
- Page 1: baseline text with no Heading or highlight applied at all (control).
- Page 2: one Heading per line, background in this order: black, dark grey, light grey, cross-hatch. Confirmed to decode as the same 2-point filled-rect TOTALPATH record already used for badges/highlights elsewhere -- solid backgrounds measure ~99% of their own bounding rect as real ink, the cross-hatch one only ~26% (still clearly real, not noise).
- Page 3: the same words, but background applied with the marker/highlighter tool instead of a Heading, in this order: black, dark grey, grey, white. The white one visibly "erases" the black text drawn under it (drawn after, same color as the page background) -- the marker-over-ink trick used since Supernote's real eraser only removes a whole stroke, not a region.

'stroke-isolation.pdf' is Supernote's own vector export of 'stroke-isolation.note', all 5 pages. It is the best width ground truth in the corpus because the exporter uses two styles -- filled outlines for some strokes, stroked polylines carrying an explicit `w` for others -- and page 4 (one needle-pen stroke per width setting) comes out as the second kind, so the device states each width as a number instead of drawing a shape to measure: 12, 7, 4, 2 against `strokeRenderWidth`'s 12.01, 7.02, 4.05, 1.99. Page 2 separates the four pen tools and page 3 the four colours (note page 3 is the newer ink pen `pen=16`, not the needle pen, which is what explains its widths sitting ~0.82x nominal). See plans/vector-format-spec.md's thickness section.

'headings-and-marker.pdf' is Supernote's own PDF export of 'headings-and-marker.note' (from the on-device/desktop export feature, not produced by this library), used as external ground truth for issue #56's follow-up: each page's ink is drawn as a real vector `/Annots` "Stamp" appearance stream (actual `m`/`l`/`c` path operators with real stroke/fill colors and widths), not just a rasterized image. Page 1's 32 stroked subpaths match `parseStrokes`' own decoded stroke count for that page exactly, and pages 2/3's 4 fill colors give exact canonical RGB values for Supernote's "dark grey"/"light grey" -- notably *different* from what this library's own raster-based color sampling measures for the same page (see `sampleStrokeStyle` in `src/svg.ts`), most likely because the on-device ink bitmap is quantized to a small set of e-ink grey levels while the PDF export's vector fill uses the unquantized design color.

'erase.note' + 'erase.pdf' exercise every erase mechanism on one N5 (Manta) page, with the PDF (Supernote's own vector export) as ground truth -- the export draws *only* the white cover-up ink, confirming every dark stroke counts as erased on-device. Rows top to bottom, each drawn then erased a different way:
- Rows 1-2 (needle line, marker band): erased with the drag eraser -- recorded as `pen=3, color=255, thickness=400` path records.
- Rows 3-4 (needle line, marker bands): erased with a bigger/other eraser mode -- `pen=9, color=255, thickness=1400` records. Notably row 3's line extends past every recorded eraser path's own geometry yet is fully erased, proving stroke visibility is NOT recoverable by replaying eraser paths (see plans/vector-format-spec.md's erase-records section).
- Rows 4-5 also include white-ink cover-ups (`color=254` marker/needle scrubs) -- real ink, exported in the PDF, hiding earlier dark ink by paint-over.
- Row 6 (light-grey line): lasso-selected and deleted -- the selection loop survives as two byte-identical `pen=4, color=0, thickness=200` records (never rendered by the device), while the deleted line itself also stays in TOTALPATH.

'horizontal_1270.pdf', 'nomad-3.15.27-blank-shapes-and-RTR.pdf', 'nomad-3.26.40-blank-2p.pdf', 'stroke-isolation.pdf', 'turkish.pdf' are Supernote's own PDF exports of the same-named .note fixtures, added as additional device ground truth. horizontal_1270.pdf uses the older stroked-polyline export style (its page draws exactly 61 of the note's 82 decodable ink strokes -- the other 21 are erased, a per-stroke visibility count this library's tests use); the nomad/turkish/stroke-isolation ones use the newer filled-outline style (pressure-varying width as filled Bezier contours).

'erase-no-white-pen.note' + 'erase-no-white-pen.pdf' are the clean companion to 'erase.note': four lines, each in a different pen (marker, calligraphy, ink pen, needle pen), every one of them erased -- by the drag eraser, the lasso eraser, and lasso-select-and-delete -- with **no white-ink cover-up strokes** to muddy the comparison. The rendered page is blank and the PDF export draws nothing, so every ink record in TOTALPATH is known-erased. This is the fixture that disproved the "point_contour records what survived erasing" hypothesis: all five strokes still carry full-area rendered outlines (see plans/vector-format-spec.md's point_contour section). It also isolates the lasso record type cleanly (two byte-identical `pen=4` records, positions 7 and 8).

'a5x-2.14.28.pdf' is Supernote's own vector export of 'a5x-2.14.28.note', and a rare 1:1 ground truth: its filled-outline stream holds exactly 146 filled shapes for that page's exactly 146 decoded strokes, so each stroke's rendered ink area can be compared directly against the device's own. Used to establish that `thickness` is the tool's *configured* width rather than its rendered one -- this page's older ink pen (`pen=1`, `thickness=200`, i.e. 2px nominal) really renders ~4.4px, so drawing at nominal laid down only 40% of the device's ink. See plans/vector-format-spec.md's thickness section.

'caligraphy.note' + 'caligraphy.pdf' isolate the calligraphy pen (`pen=15`), the one tool whose rendered width errs in the *opposite* direction to the older ink pen. Pages 1-3 are nothing but calligraphy at three width settings (`thickness` 600/900/1200) in three colours (black, 157, 201); page 4 is a full page of it erased down to the single surviving word "Erase" (via the drag eraser, the lasso eraser, and lasso-select-delete, so it doubles as erase ground truth). The PDF is Supernote's own vector export, in the filled-outline style with fills grouped per colour rather than per stroke, so it's compared by total ink area per page rather than 1:1. It establishes that a chisel nib lays down only ~0.35-0.45x the ink its configured width implies -- drawing these at nominal covers ~1.9x the device's ink. See plans/vector-format-spec.md's thickness section.

'erase-colors.note' + 'erase-colors.pdf' put grey (158) marker bands and black (0) pen writing next to each other and then erase some of each, which is the case that would catch the survival check's colour matching being too loose (deciding what an eraser left behind compares each stroke's colour against the rendered ink, so a grey stroke could otherwise "survive" on a black neighbour's ink). Page 1 has no erasers and acts as the control -- the fraction of the device's ink we draw there is width accuracy alone; page 2 is the same content erased, and its ratio matching page 1's is what shows the erase decisions aren't skewing. Both land at 0.95, the closest of any fixture. Note it does *not* exercise the tightest case: dark grey (158) against light grey (201) differ by less than the matcher's tolerance, so a page with those two adjacent and one erased would still be worth having.

'straight-line.note' + 'straight-line.pdf' are the only fixture using the ruler/straight-line tool, and the only source of `stroke_kind: "straightLine"` ([feature description](https://supernote.com/blogs/supernote-blog/introducing-the-smart-straight-line-feature-and-smoother-handwriting-strokes)). Page 1 is six lines (a cross and an asterisk), page 2 two more, page 3 a freehand stroke that was erased away. It turned out to matter rather than being a loose end: those records store only their two endpoints, and `vectorInk` was treating *any* two-point record as a filled rectangle, so page 1's six lines rendered as three invisible degenerate boxes and no lines at all. `stroke_kind` is what separates the three unrelated things that store two points -- a Heading/badge rectangle (`"0001"`), a ruler line (`"straightLine"`), and an ordinary ink dot (`"others"`). See plans/vector-format-spec.md's `stroke_kind` table.

'erase-pen.note' + 'erase-pen.pdf' erase with a *white pen* rather than the eraser tool, which is the partial-erase mechanism available on this device. Pages 1-3 each pair a dark stroke with a white one drawn across it (needle pen, marker, and a long dense scribble); page 4 is the control, dark only. Nothing is erased in the format sense: both strokes are ordinary ink, neither carries an erase mark, and the page renders correctly by drawing them in order rather than by working out what survived -- Supernote's own export does the same, setting fill colour black then white in that sequence. What it guards is the ordering, which isn't free: `buildStrokePathElements` sorts strokes into tiers instead of keeping TOTALPATH order, so a cover-up landing in a different tier from the ink it covers would be painted underneath it.

'sticker.note' is the first fixture from Supernote's plugin support (beta), covering the built-in "sticker" plugin -- see https://github.com/philips/supernote-typescript/issues/68. A sticker turns out to need no new container at all: placing one writes its artwork into the page's ordinary TOTALPATH as plain stroke records, so no new tag, address or section appears anywhere in the file. What it does do is push a stroke shape the centreline model can't express. Pages are 1-indexed:
- Page 1: a hand-drawn smiley (5 ordinary strokes) -- the control, saved before any sticker was placed.
- Page 2: one placed sticker (50 records) plus a marker stroke drawn across it. The sticker's artwork is built the way a person fills a shape with a pen: black strokes doubling back over themselves to lay down a solid region, then white (`color=254`) strokes carved back over the top for the eyes, nose and tie. Drawn as uniform-width centrelines those fill strokes came out as the hollow scribble that traces the fill rather than the filled shape, and one record -- the silhouette -- has no sampled points at all, only a `point_contour` outline, so it rendered as nothing whatsoever. Drawing each stroke as its own `point_contour` outline is what reproduces it: measured against the page's own render, that takes this page from 6,892 disagreeing pixels to 1,874. See plans/vector-format-spec.md's `point_contour` section.
- Page 3: blank.

'sticker.pdf' is Supernote's own vector export of 'sticker.note' (attached to issue #68 alongside the note itself), and the ground truth for the page above. Page 1 is a clean 1:1: five filled outlines for the control's five decoded strokes, at 0.85x their ink. Page 2 is the interesting one, and the fixture site's ink ratio is wrong about it — the exporter merges every black ring on the page into one filled path, whereas we draw the sticker's fill as the 22 separate overlapping outlines the records actually describe, and the site's measure sums per-path areas rather than unioning them. Summed, ours reads 57,668 square pixels against the device's 42,800, or 1.36x. Rasterised and unioned, the two cover 42,704 and 42,800 — agreement to within 0.3%, on the page that motivated drawing strokes as `point_contour` outlines in the first place. Worth remembering before reading that page's amber ratio as a regression. The export has ink for pages 1-2 only; page 3 is blank on both sides.

'nomad-3.26.40-link-tag-3p.note' + 'nomad-3.26.40-link-tag-3p.pdf' are the only fixture covering *partial* erasing, because this firmware is the only one here that splits a stroke rather than removing it whole. Its export (Supernote's own, stroked-polyline style on page 3 and filled outlines on pages 1-2) is the ground truth for both halves of `m_trailStatus` -- see plans/vector-format-spec.md's Part 1.4.
- Page 1: plain writing, nothing erased, no marked records at all.
- Page 2: an eraser dragged four times across seven pen lines of increasing width, plus three marker strokes erased the same way. Each erased record is marked `m_trailStatus = -4` and the pieces the eraser left behind are written as *separate* records holding only a `point_contour` and no points. The export draws exactly those pieces -- 5, 4, 4, 5, 5, 5, 5 across the seven lines, matching the fragment records' own positions to within a pixel -- and never a path spanning the line they came from.
- Page 3: writing that was erased and then rewritten in the same place, which is the page that punishes deciding what survived by sampling the render: a stroke's own ink and its replacement's are in the same spot, so 15 of its 30 erased strokes measure as still present. The export draws 113 paths for the 113 records reading `0`, and none of the 30 marked ones. It also holds the Keyword/Tag lasso loops and link-tag boxes the parser filters out.
